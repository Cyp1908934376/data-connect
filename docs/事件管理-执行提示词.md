### 0.3 Groovy 翻页实现要点

```groovy
// EVENT Groovy 脚本翻页
import groovy.json.JsonSlurper

def allRows = []
def inputRows = input.getRows()
if (inputRows.isEmpty()) return input

// 从第一页响应中提取翻页信息
def firstPage = inputRows
def totalCount = firstPage[0]?.total ?: firstPage[0]?.totalCount ?: 0
def pageSize = firstPage[0]?.pageSize ?: firstPage[0]?.size ?: 20

allRows.addAll(firstPage)

if (totalCount > 0 && pageSize > 0) {
    int totalPages = Math.ceil(totalCount / pageSize) as int
    for (int p = 2; p <= totalPages; p++) {
        def url = "https://api.nottingham.edu.cn/api/...?page=${p}&size=${pageSize}"
        def conn = new URL(url).openConnection()
        conn.setRequestProperty("Cookie", "identitytoken=...")
        conn.setRequestProperty("Accept", "application/json")
        def resp = new JsonSlurper().parse(conn.getInputStream(), "UTF-8")
        if (resp.data instanceof List) {
            allRows.addAll(resp.data)
        }
    }
}

// 返回合并后的全量数据
```

## 二、❌ 待实现：SHELL 执行器

### 2.1 需求

用户在事件管理中创建 `handlerType=SHELL` 的事件，在模板中作为 EVENT 步骤使用。

### 2.2 安全考虑（重要！）

SHELL 执行器直接执行系统命令，必须：
1. **白名单限制**：只能在配置的目录下执行
2. **命令注入防护**：参数必须转义
3. **超时控制**：防止 hang 死
4. **权限隔离**：以受限用户运行
5. **审计日志**：记录每次 shell 执行

### 2.3 实现方案

```java
// 在 EventStepExecutor.execute() 中新增分支:
} else if ("SHELL".equals(handlerType)) {
    return executeShell(handlerConfig, input, params, context);
}

/**
 * 执行 Shell 命令
 * handlerConfig 格式:
 *   cmd:echo ${sourceField}        → 简单命令
 *   script:#!/bin/bash\n...        → 多行脚本（写入临时文件执行）
 */
private DataPacket executeShell(String handlerConfig, DataPacket input,
                                 Map<String, Object> params, ExecutionContext context) {
    // 1. 判断是命令还是脚本
    String command;
    boolean isScript = handlerConfig.contains("\n") || handlerConfig.startsWith("#!");

    if (isScript) {
        // 写入临时文件，设置可执行权限
        Path tempScript = Files.createTempFile("event_", ".sh");
        Files.write(tempScript, handlerConfig.getBytes(StandardCharsets.UTF_8));
        tempScript.toFile().setExecutable(true);
        command = tempScript.toString();
    } else {
        command = handlerConfig;
    }

    // 2. 对每行数据执行命令
    List<Map<String, Object>> resultRows = new ArrayList<>();
    for (Map<String, Object> row : input.getRows()) {
        String resolvedCmd = resolveVariables(command, row, params);

        ProcessBuilder pb = new ProcessBuilder(isScript
            ? Arrays.asList("/bin/bash", resolvedCmd)
            : Arrays.asList("/bin/bash", "-c", resolvedCmd));

        // 3. 安全限制
        pb.directory(new File("/data/event_workspace"));      // 白名单工作目录
        pb.environment().remove("PATH");                       // 最小化环境
        pb.environment().put("PATH", "/usr/bin:/bin");

        Process proc = pb.start();

        // 4. 超时控制
        boolean finished = proc.waitFor(30, TimeUnit.SECONDS); // 默认30秒
        if (!finished) {
            proc.destroyForcibly();
            context.warn("Shell命令超时: " + command);
            continue;
        }

        // 5. 读取输出
        String stdout = new String(proc.getInputStream().readAllBytes(), StandardCharsets.UTF_8);
        String stderr = new String(proc.getErrorStream().readAllBytes(), StandardCharsets.UTF_8);

        if (proc.exitValue() != 0) {
            context.warn("Shell命令执行失败: exit=" + proc.exitValue() + ", stderr=" + stderr);
        }

        // 6. 解析输出（JSON行列）
        Map<String, Object> resultRow = new LinkedHashMap<>(row);
        resultRow.put("_shellOutput", stdout.trim());
        resultRow.put("_shellExitCode", proc.exitValue());
        resultRows.add(resultRow);
    }

    return DataPacket.ofList(resultRows);
}

// 变量替换：${fieldName} → row["fieldName"]
private String resolveVariables(String template, Map<String, Object> row, Map<String, Object> params) {
    String result = template;
    // 先替换行数据变量
    for (Map.Entry<String, Object> entry : row.entrySet()) {
        result = result.replace("${" + entry.getKey() + "}",
            entry.getValue() != null ? entry.getValue().toString() : "");
    }
    // 再替换事件参数
    for (Map.Entry<String, Object> entry : params.entrySet()) {
        result = result.replace("${" + entry.getKey() + "}",
            entry.getValue() != null ? entry.getValue().toString() : "");
    }
    return result;
}
```

### 3.2 实现方案

```java
@Autowired
private VisualTemplateExecutionService executionService;

/**
 * 调用模板作为事件
 * handlerConfig = 模板ID (数字)
 */
private DataPacket executeTemplateEvent(String templateIdStr, DataPacket input,
                                         Map<String, Object> params, ExecutionContext context) {
    Long templateId = Long.parseLong(templateIdStr.trim());
    context.info("事件调用模板: templateId=" + templateId);

    // 将 params 合并到 input 的第一行（如果存在）
    DataPacket enrichedInput = input;
    if (!params.isEmpty() && input.getFirstRow() != null) {
        Map<String, Object> enrichedRow = new LinkedHashMap<>(input.getFirstRow());
        enrichedRow.putAll(params);  // 事件参数覆盖/补充行数据
        enrichedInput = DataPacket.of(enrichedRow);
    }

    return executionService.execute(templateId, enrichedInput);
}
```

### 3.3 循环引用检测（重要！）

TEMPLATE 事件可能导致模板 A → 模板 B → 模板 A 的无限递归：

```java
// 在 ExecutionContext 中加入调用链追踪
public class ExecutionContext {
    private final Set<Long> callChain = new LinkedHashSet<>();

    public void enterTemplate(Long templateId) {
        if (!callChain.add(templateId)) {
            throw new RuntimeException("检测到循环模板调用: " + callChain + " → " + templateId);
        }
    }

    public void exitTemplate(Long templateId) {
        callChain.remove(templateId);
    }
}
```

在 `VisualTemplateExecutionService.execute()` 中：
```java
public DataPacket execute(VisualTemplate template, DataPacket input) {
    // ...
    context.enterTemplate(template.getId());
    try {
        // ... 执行逻辑
    } finally {
        context.exitTemplate(template.getId());
    }
}
```

## 四、🔶 边界情况与刁钻场景（仅文档，未落地）

### 4.1 深层嵌套 EVENT 链

**场景**：模板中连续多个 EVENT 步骤，前一个的输出是后一个的输入

```
DATA_SOURCE → EVENT(MD5) → EVENT(Base64) → EVENT(掩码) → OUTPUT
   ↓              ↓             ↓              ↓
 [{name,phone}]  [{...,       [{...,         [{...,
                  phone:md5}]   phone:md5     phone:md5
                                → base64}]    → base64
                                              → mask}]
```

**当前问题**：
- `EventStepExecutor` 按 `sourceField` 查找字段，如果前一步改了字段名就找不到
- 例如：MD5 输出到 `phoneHash`，下一步 Base64 的 `sourceField=phone` 就匹配不到

**要求**：
- EVENT 步骤应支持 `targetField` 参数，明确指定输出字段
- 事件链中每步的 source/target 字段映射关系要清晰
- 需要在前端渲染时提示可用字段（上一步的输出字段列表）

### 4.2 事件 + 映射的交互

**场景**：EVENT 修改字段后，MAPPING 步骤再重命名

```
EVENT(MASK_PHONE, sourceField=phone) → MAPPING(phone→maskedPhone, name→userName)
```

**当前行为**：EVENT 在原字段上修改 → MAPPING 读取修改后的值 → 正常

**边界问题**：如果 MAPPING 的 src 和 dst 相同时，且前置 EVENT 也操作同一字段
```
EVENT(MASK_PHONE, sourceField=phone) → MAPPING(phone→phone)
```
这会导致脱敏后的值被原始值覆盖（如果 MAPPING 不区分先后顺序）。当前代码是按行逐条映射的，应该没问题。但如果 MAPPING 是批量操作就有问题。

### 4.3 输入为空数据

**场景**：上游 DATA_SOURCE 返回 0 行，EVENT 步骤仍会执行

```java
// EventStepExecutor.execute() → executeBuiltin()
List<Map<String, Object>> rows = input.getRows();  // rows = []
for (Map<String, Object> row : rows) {
    // 循环体不执行，返回空 DataPacket
}
return DataPacket.ofList(resultRows);  // 返回空列表，不报错
```

**当前行为**：静默返回空数据 ✅ 合理

**但**：如果步骤链是 `EVENT → OPERATION(DB_INSERT)`，空数据会导致 INSERT 步骤收到空行，应当提前终止并给出明确提示。

**建议**：在 `VisualTemplateExecutionService.executeEventSteps()` 的步骤循环中加入空数据短路：

```java
if (currentData.isEmpty() && !"DATA_SOURCE".equals(stepType)) {
    context.warn("步骤 " + stepType + " 收到空数据，跳过后续步骤");
    break;
}
```

### 4.4 源字段不存在

**场景**：EVENT 指定 `sourceField=phoneNumber`，但上游数据只有 `phone` 字段

```java
// applyFieldTransform()
Object value = row.get(sourceField);  // value = null
if (value != null) {
    row.put(targetField, transform.apply(value.toString()));
}
// value 为 null → 什么都不做，静默跳过
```

**当前行为**：静默跳过，该行不变，不报错 ❌ 不够好

**建议**：
- 在 `params` 中增加 `required: true/false`
- 如果 `required=true` 且字段不存在，应报错
- 在 `inputSchema` 的字段定义中设置 `required`，前端 redner 时传入

### 4.5 大数据量性能

**场景**：API 返回 10000 行，每行执行 EVENT（如 MD5 哈希）

**当前**：`for` 循环逐行处理，单线程。10000 行 MD5 不是问题。

**但如果**：EVENT 是 GROOVY 脚本，其中包含网络请求或复杂计算，10000 行就会很慢。

**建议**：
- 加入 `parallelism` 参数，支持并行处理
- 加入 `batchSize` 参数，分批处理并显示进度

### 4.6 Groovy 脚本安全性

**场景**：用户编写 Groovy 脚本事件

```groovy
// 恶意脚本
System.exit(0)
Runtime.getRuntime().exec("rm -rf /")
```

**当前**：Groovy 脚本运行在 JVM 进程内，有完整的系统权限 ❌ 极度危险

**建议**：
1. **沙箱限制**：使用 `SecureASTCustomizer` + `CompilerConfiguration` 限制可用类
2. **超时控制**：脚本执行超时自动终止
3. **脚本审核**：管理员审批后才能启用

```java
import org.codehaus.groovy.control.customizers.SecureASTCustomizer;
import org.codehaus.groovy.control.CompilerConfiguration;
import org.kohsuke.groovy.sandbox.GroovySandbox;

private Object executeGroovySandboxed(String script, Map<String, Object> bindings) {
    // 白名单：只允许使用以下类
    SecureASTCustomizer secure = new SecureASTCustomizer();
    secure.setAllowedImports(Arrays.asList(
        "java.util.*", "java.lang.*", "java.math.*",
        "com.dataconnect.component.DataPacket"
    ));
    // 禁止：System, Runtime, File, ProcessBuilder, Class, ClassLoader
    secure.setDisallowedStaticImports(Arrays.asList(
        "java.lang.System", "java.lang.Runtime"
    ));

    CompilerConfiguration config = new CompilerConfiguration();
    config.addCompilationCustomizers(secure);

    GroovyShell shell = new GroovyShell(config);
    // ... 在沙箱中执行
}
```

### 4.7 事件参数中引用模板输入参数

**场景**：EVENT 步骤的 `sourceField` 不是固定值，而是从模板输入参数中来

当前 EVENT 参数都是静态配置的（如 `sourceField: "phone"`），如果要动态指定：

```json

  "eventCode": "MASK_PHONE",
  "params": {
    "sourceField": "${input.targetField}"   // 从模板输入参数动态获取
```


### 4.8 事件在 CALL_TEMPLATE 子流程中的应用

**场景**：父模板输出模式 `CALL_TEMPLATE(ROW)`，逐行调用子模板，子模板中有 EVENT 步骤

```
父模板:
  DATA_SOURCE(查10条) → OUTPUT(CALL_TEMPLATE, passMode=ROW)
       ↓
子模板 (每行调一次):
  MAPPING → EVENT(MD5) → OPERATION(DB_INSERT)
```

**当前行为**：✅ 可以工作。每次 ROW 调用都是一个独立的 `execute()`，子模板中的 EVENT 正常执行。

**但**：如果 10000 行 × 每行调子模板 = 10000 次 EVENT 调用。性能问题。

### 4.9 事件失败后的数据完整性

**场景**：步骤链 `EVENT_A → EVENT_B → OPERATION`，B 失败

```
当前行为: EventStepExecutor 捕获异常返回 DataPacket.error()
        → executeEventSteps 中 currentData 变为 error DataPacket
        → 后续步骤收到 error DataPacket → 可能产生非预期行为
```

**建议**：增加 `onError` 策略：
- `STOP` (默认) — 立即终止整个流程
- `SKIP` — 跳过当前行，继续处理下一行
- `FALLBACK` — 使用默认值填充

### 4.10 事件嵌套深度限制

**场景**：A → B(TEMPLATE事件) → C(TEMPLATE事件) → D(TEMPLATE事件) → ...

**建议**：设置最大嵌套深度（如 10 层），超过后报错 `EVENT_NESTING_TOO_DEEP`。

### 4.11 事件热更新

**场景**：事件定义在运行时被修改，正在执行的模板使用旧定义

**当前**：每次执行时从数据库读取事件定义 → ✅ 自然支持热更新

**但**：如果事件被删除，正在运行的流程会报 `EVENT_NOT_FOUND`。

### 4.12 跨模板事件复用冲突

**场景**：模板 A 和模板 B 都使用事件 `MASK_PHONE`。管理员修改了 `MASK_PHONE` 的 Groovy 脚本。

**影响**：A 和 B 下次执行时都会使用新脚本 → 这种"全局影响"可能导致非预期的行为变化。

**建议**：
- 事件修改时记录版本号
- 模板中可锁定事件版本
- 修改事件时提示"被 N 个模板引用"

## 4.13 EVENT 步骤在管道中的位置与能力边界

### 4.13.1 管道结构与 EVENT 插入点

可视化模板的步骤是**线性串联**的，EVENT 可以放在任意位置：

```
INPUT ─┬─> DATA_SOURCE ─┬─> MAPPING ─┬─> FILTER ─┬─> CALL_TEMPLATE ─┬─> OPERATION ─┬─> OUTPUT
       │                │            │           │                  │              │
       ├─ EVENT.1       ├─ EVENT.2   ├─ EVENT.3  ├─ EVENT.4        ├─ EVENT.5     ├─ EVENT.6
       │                │            │           │                  │              │
       ▼                ▼            ▼           ▼                  ▼              ▼
    改输入参数       翻页/数据清洗  字段格式转换   数据裁剪/校验    写前预处理       最终编码
```

每个位置能干的事：

| 位置 | 当前数据 | 适合做的事 |
|------|---------|-----------|
| ① INPUT 之后 | 模板输入参数 | 校验必填项、默认值填充、参数转换 |
| ② DATA_SOURCE 之后 | API/DB 查回来的数据 | **翻页循环、跨数据源补全、行级查漏补缺** |
| ③ MAPPING 之后 | 字段已映射的数据 | 格式转换、脱敏、编码、脚本计算 |
| ④ 多个 EVENT 链 | 上一步处理结果 | 分阶段处理：先脱敏→再编码→再加密 |
| ⑤ OUTPUT 之前 | 最终要输出的数据 | 最终校验、补充时间戳、序列化准备 |

### 4.13.2 跨数据源场景分析

**场景：数据源 A → 需要数据源 B 补全**

| A 类型 | B 类型 | 能？ | 方案 |
|--------|--------|:--:|------|
| API | API | ✅ | Groovy EVENT 发 HTTP 调 B，合并字段 |
| API | DB | ⚠️ | 用 CALL_TEMPLATE(ROW) → 子模板的 DATA_SOURCE 连 B 的 DB |
| DB | API | ✅ | Groovy EVENT 发 HTTP 调 B |
| DB | DB | ⚠️ | 同上，CALL_TEMPLATE(ROW) → 子模板 |
| API | API (翻页) | ✅ | Groovy EVENT 解析 totalCount → for 循环翻页 → 合并 |

**场景：两个数据源做 JOIN**

❌ 做不到。管道是串联的，DATA_SOURCE 会**覆盖**上一个 DATA_SOURCE 的结果，不是追加。无法实现 SQL 的 JOIN 语义。

**场景：条件分支（if X→走步骤A else→走步骤B）**

❌ 做不到。步骤列表是线性的 `for (step : steps)`，没有条件跳转。

### 4.13.3 三大核心限制

> **限制一：Groovy EVENT 拿不到系统数据源的数据库连接池**
>
> Groovy 脚本运行在 `EventStepExecutor` 的 `ScriptEngine` 中，无法访问 Spring 容器中的 `DataSourceService`、`DynamicDsManager` 等 Bean。如果需要对系统内已配置的数据库做查询，必须在 Groovy 里手写 JDBC URL + 用户名密码。替代方案是用 CALL_TEMPLATE(ROW) + 子模板的 DATA_SOURCE 步骤。

> **限制二：管道是严格线性的，不能并行、不能分支、不能 JOIN**
>
> 步骤在 `VisualTemplateExecutionService` 中是 `for (step : steps)` 顺序执行，`currentData` 被逐步覆盖。不支持：
> - **条件分支**：根据当前数据动态决定下一步走什么
> - **并行取数**：同时调两个 API 然后合并
> - **JOIN**：两个 DATA_SOURCE 的结果按字段关联
> - **循环**：除了 CALL_TEMPLATE(ROW) 的隐式逐行循环外，没有显式循环结构

> **限制三：EVENT 是无状态的，不能跨执行持久化**
>
> 每次模板执行都是独立的，Groovy 脚本运行在全新的 `ScriptEngine` 上下文中。无法：
> - 读写文件记录"上次推到哪了"（SYNCED_SET 去重）
> - 跨行累计计数器（除非存在 DataPacket 的行数据中）
> - 记录整个管道执行过程中的中间状态到外部存储
>
> 需要持久化的场景（如增量同步去重）必须在 EVENT 之外解决，比如新建 BUILTIN 事件用 DB 表记录状态。

## 六、✅ 完整的事件生命周期（已实现部分）

```
┌─────────────────────────────────────────────────────────────┐
│                     事件管理 CRUD                           │
│  /event/list → 列表  /event/form → 创建/编辑               │
│  /event/save → 保存  /event/delete/{id} → 删除              │
│                                                             │
│  创建事件:                                                  │
│  1. 填写基本信息 (name, code, category)                     │
│  2. 定义输入参数 (inputSchema JSON)                         │
│  3. 配置执行器 (handlerType + handlerConfig)               │
│  4. 保存 → event_definition 表                              │
│                                                             │
│  在模板中使用:                                              │
│  1. 模板编辑器 → 添加步骤 → "事件处理"                      │
│  2. 下拉框通过 /event/api/list 加载事件列表                  │
│  3. 选中事件 → 根据 inputSchema 渲染参数表单                 │
│  4. 保存模板 → eventConfig.steps 中记录:                    │
│     {"type":"EVENT", "eventCode":"MASK_PHONE", "params":{...}}│
│                                                             │
│  执行时:                                                    │
│  1. VisualTemplateExecutionService 遍历 steps              │
│  2. type=EVENT → executeEventStep()                        │
│  3. EventStepExecutor.execute()                            │
│  4. 根据 eventCode 查 EventDefinition                      │
│  5. 根据 handlerType 执行:                                  │
│     - BUILTIN → executeBuiltin(handlerConfig, input, params)│
│     - GROOVY → executeGroovy(handlerConfig, input, params)  │
│     - SHELL  → executeShell(handlerConfig, input, params)   │
│     - TEMPLATE → executeTemplateEvent(handlerConfig, ...)   │
│  6. 返回处理后的 DataPacket → 进入下一步或输出              │
└─────────────────────────────────────────────────────────────┘
```
