## 一、输出事件重设计 — ✅ 全部完成

### 1.1 当前问题

输出事件有 4 个选项但后端只实现了 RETURN：

| 选项 | 前端 | 后端 |
|------|------|------|
| RETURN (返回给调用方) | ✅ | ✅ |
| DATABASE (写入数据库) | ✅ | ❌ 空壳 |
| API (调用API) | ✅ | ❌ 空壳 |
| FILE (写入文件) | ✅ | ❌ 空壳 |

而 DATABASE/API/FILE 的能力和操作事件高度重叠，不应在输出事件中重复实现。

### 1.2 新设计：精简为 3 个输出方式

```
┌─ 输出事件 ───────────────────────────────────────────┐
│                                                        │
│ 输出方式: ○ 默认返回  ○ 调用模板处理  ○ 写出文件       │
│                                                        │
│ ┌──────────────┬──────────────────────────────────┐   │
│ │ 默认返回      │ 原样返回上游数据，不做任何处理    │   │
│ │              │ 可选: 通过输出参数定义提取字段     │   │
│ ├──────────────┼──────────────────────────────────┤   │
│ │ 调用模板处理  │ 将当前数据传给另一个模板，        │   │
│ │              │ 由该模板负责落库/调API等实际操作   │   │
│ ├──────────────┼──────────────────────────────────┤   │
│ │ 写出文件      │ 将数据写成文件 (JSON/CSV/XML)     │   │
│ │              │ 指定路径、格式、写入模式           │   │
│ └──────────────┴──────────────────────────────────┘   │
│                                                        │
└────────────────────────────────────────────────────────┘
```

### 1.3 各方式详细设计

#### A. 默认返回（RETURN）

```
输出方式: ● 默认返回

输出参数 (可选，用于提取/重命名字段):
┌─ 返回字段名 ──┬─ 数据源字段 ────────────────┐
│ userId        │ id                        [✕] │
│ userName      │ name                      [✕] │
│ userSalary    │ salary                    [✕] │
└───────────────┴───────────────────────────┘
[+ 添加输出参数]

不配输出参数时 → 返回全部字段
配了输出参数时 → 只返回指定字段，并可重命名
```

#### B. 调用模板处理（CALL_TEMPLATE）

```
输出方式: ● 调用模板处理

说明: 将当前数据传给指定模板，由该模板完成实际落库/调API/写文件等操作

选择模板: [保存到MySQL_v1 ▼]    (展示所有可用模板)

传递方式: ○ 整包传递(原样传入子模板)
          ○ 逐行传递(每行触发一次子模板)
          ○ 分批传递(每 [100] 行一批)

超时设置: [60] 秒  (单次调用超时)
失败处理: ○ 忽略继续  ○ 停止并报错  ○ 重试 [3] 次

典型场景:
- 数据查出来 → 输出事件调用"写入MySQL模板" → 该模板内是 INSERT 操作
- 数据查出来 → 输出事件调用"发送通知模板" → 该模板内是 API_CALL 操作
```

**为什么这样做**: 把"怎么落库"的逻辑封装在独立模板中，输出事件只负责"交给谁处理"。模板可复用、可独立测试。

#### C. 写出文件（FILE）

```
输出方式: ● 写出文件

文件路径: [/data/output/${date}/${templateName}.json]
          可用变量: ${date} ${time} ${templateName} ${timestamp}

文件格式: [JSON ▼]  JSON / CSV / XML / TXT / 自定义模板

JSON选项 (格式=JSON时):
  ○ 紧凑(一行)  ● 格式化(缩进)  ○ JSON Lines(每行一个JSON)

CSV选项 (格式=CSV时):
  ☑ 包含表头  ☐ 自定义分隔符: [,]

写入模式: ○ 覆盖  ○ 追加  ○ 按日期分文件

编码: [UTF-8 ▼]

[预览内容...]  [执行写出]
```

### 1.4 后端改动

```java
// 在 executeEventSteps 中替换原来的输出处理
String outputTarget = (String) outputConfig.getOrDefault("outputTarget", "RETURN");
String outputMode = (String) outputConfig.getOrDefault("outputMode", "RETURN"); // 新增

switch (outputMode) {
    case "RETURN":
        return buildReturnResult(currentData, template.getOutputParams());
    case "CALL_TEMPLATE":
        return executeOutputViaTemplate(currentData, outputConfig, context);
    case "FILE":
        return executeOutputToFile(currentData, outputConfig, context);
    default:
        return currentData;
}
```

### 1.5 前端改动

- 删除原来 `outputTarget` 下拉的 DATABASE/API 选项
- 新增 `outputMode` 单选：默认返回 / 调用模板处理 / 写出文件
- 每种模式切不同的配置面板

## 二、事件管理系统 — 🔶 部分完成

### 2.1 定位

"事件" = 一种**可注册、可配置、可复用**的数据处理单元。不局限于输出事件，可在模板的任意步骤中使用。

### 2.2 概念模型

```
事件管理 (Event Registry)
  ├── 内置事件 (系统预置，不可删除)
  │   ├── base64编码
  │   ├── base64解码
  │   ├── 二进制处理
  │   ├── 图片处理 (缩放/裁剪/格式转换)
  │   ├── WebService调用 (SOAP)
  │   ├── 加密/解密 (AES/RSA/MD5)
  │   └── 数据脱敏 (手机号/身份证/银行卡)
  │
  └── 自定义事件 (后台管理添加)
      ├── 用户自定义事件1
      └── 用户自定义事件2
```

### 2.3 事件定义结构

```json
{
  "id": 1,
  "name": "base64编码",
  "code": "BASE64_ENCODE",
  "category": "编码转换",      // 分类
  "description": "将指定字段值编码为Base64",
  "icon": "bi bi-shield-lock",
  
  "inputSchema": {             // 输入参数定义
    "fields": [
      {"name": "sourceField", "label": "源字段", "type": "string", "required": true,
       "description": "需要编码的字段名"},
      {"name": "targetField", "label": "目标字段", "type": "string", "required": false,
       "description": "编码后输出的字段名，默认覆盖源字段"}
    ]
  },
  
  "outputSchema": {            // 输出说明
    "type": "FIELD_MODIFY",
    "description": "对指定字段进行Base64编码"
  },
  
  "handler": {                 // 执行器
    "type": "BUILTIN",         // BUILTIN / GROOVY / SHELL
    "className": "com.dataconnect.event.handler.Base64EncodeHandler"
  }
}
```

### 2.4 事件分类

| 分类 | 内置事件 | 说明 |
|------|---------|------|
| **编码转换** | BASE64_ENCODE, BASE64_DECODE, URL_ENCODE, URL_DECODE, HEX_ENCODE | 编码解码 |
| **数据处理** | BINARY_TO_STRING, STRING_TO_BINARY, BYTE_ARRAY, COMPRESS, DECOMPRESS | 二进制/压缩 |
| **图片处理** | IMAGE_RESIZE, IMAGE_CROP, IMAGE_FORMAT, IMAGE_TO_BASE64, BASE64_TO_IMAGE | 图片操作 |
| **WebService** | SOAP_CALL, XML_PARSE, XML_BUILD | SOAP/XML |
| **加密安全** | AES_ENCRYPT, AES_DECRYPT, RSA_ENCRYPT, MD5_HASH, SHA256_HASH | 加解密 |
| **数据脱敏** | MASK_PHONE, MASK_IDCARD, MASK_BANKCARD, MASK_NAME, MASK_EMAIL | 脱敏 |
| **格式转换** | JSON_TO_XML, XML_TO_JSON, CSV_TO_JSON, JSON_TO_CSV | 格式互转 |

### 2.5 使用方式

#### 在模板步骤中使用

添加步骤 → **事件处理**（新增步骤类型 `EVENT`）

```
┌─ 事件处理步骤 ────────────────────────────────────┐
│                                                      │
│ 选择事件: [base64编码 ▼]  (从事件管理中加载)          │
│                                                      │
│ ── 事件参数 ──────────────────────────────           │
│ 源字段:   [password         ]                        │
│ 目标字段: [encodedPassword  ]                        │
│                                                      │
│ [预览处理结果]                                       │
└──────────────────────────────────────────────────────┘
```

#### 步骤配置 JSON

```json
{
  "type": "EVENT",
  "eventCode": "BASE64_ENCODE",
  "params": {
    "sourceField": "password",
    "targetField": "encodedPassword"
  }
}
```

### 2.7 事件执行器类型

| 类型 | 说明 | 适用场景 |
|------|------|---------|
| `BUILTIN` | Java 类实现，系统内置 | 预置的标准事件 |
| `GROOVY` | Groovy 脚本，动态编译执行 | 自定义事件，灵活修改 |
| `SHELL` | Shell/Python 命令行调用 | 调用外部脚本 |
| `TEMPLATE` | 调用另一个可视化模板作为事件 | 复杂组合逻辑 |

### 2.8 可在任意步骤中使用

事件不限制使用位置：

```
输入 → 数据源查询 → [事件:脱敏] → 映射 → [事件:base64] → 输出
                     ↑                          ↑
                 中间步骤使用               输出前使用
```

在前端添加步骤弹窗中新增选项：

```html

    <br><small class="text-muted">编码/加密/脱敏/格式转换等</small>
```

## 三、数据模型

### 3.1 事件定义表 `event_definition`

```sql
CREATE TABLE event_definition (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    code VARCHAR(100) NOT NULL UNIQUE,
    category VARCHAR(50),
    description VARCHAR(500),
    icon VARCHAR(50) DEFAULT 'bi-lightning',
    input_schema TEXT,              -- JSON: 输入参数定义
    output_schema TEXT,              -- JSON: 输出说明
    handler_type VARCHAR(20) DEFAULT 'GROOVY',  -- BUILTIN/GROOVY/SHELL/TEMPLATE
    handler_config TEXT,             -- 类名 / Groovy脚本 / Shell命令 / 模板ID
    is_builtin INT DEFAULT 0,       -- 1=内置不可删
    is_enabled INT DEFAULT 1,
    create_time TIMESTAMP,
    update_time TIMESTAMP
);
```

### 3.2 输出事件配置结构（eventConfig 中的 output）

```json
{
  "output": {
    "outputMode": "RETURN",        // RETURN | CALL_TEMPLATE | FILE
    "outputParams": [...],          // RETURN 模式时可选
    
    // CALL_TEMPLATE 模式:
    "callTemplateId": 5,
    "passMode": "PACKET",          // PACKET(整包) | ROW(逐行) | BATCH(分批)
    "batchSize": 100,
    "timeout": 60,
    "onError": "STOP",             // IGNORE | STOP | RETRY
    "retryCount": 3,
    
    // FILE 模式:
    "filePath": "/data/output/${date}/result.json",
    "fileFormat": "JSON",          // JSON | CSV | XML | TXT
    "fileOptions": {
      "pretty": true,              // JSON格式化
      "includeHeader": true,       // CSV表头
      "delimiter": ",",
      "encoding": "UTF-8"
    },
    "writeMode": "OVERWRITE"       // OVERWRITE | APPEND | DAILY
  }
}
```
